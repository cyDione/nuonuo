# 对照审查：文章、DS 原型与当前实现（2026-11-04）

对照了三份材料：重读的《Super-agent 设计探索》全文、dsh-superagent-prototype 的 docs/000–008，以及 Muse / Grok Bot 的公开资料。下面逐条列出偏差和遗漏，以及打算怎么改。

## 一、前端：对话里暴露了不该暴露的东西

文章和原型里有几条原则，现在的界面都违背了：

- 文章 §2.2：「Worker 不会直接与人类交互，**其推理过程和工具调用不会直接输出到外部信道**，而是向 Router 层汇报，由 Router 层统一向用户回复。」
- 文章 §2：「Session 应当是系统的实现细节，而不应是用户的认知负担。」
- 文章 §2.2：「个人助手在界面上通常只提供一个单会话的聊天页面……底层可以为每个话题分别分派 Worker。」
- 原型 000：「只用尽量少的注意力」；「健康的状态不占任何空间」。

现在网页对话也是一个信道，却把下面这些直接摆给了你：

- **任务卡片**：阶段术语（进行中 / 等待中 / 已结束）、工作目录、Worker 正在输出的文字、Worker 的原始汇报。
- **「查看过程」**：可以展开看到每次工具调用、命令和输出。
- **右侧常驻面板**：显示「进行中 / 最近结束」，状态正常时也占着一块屏幕。
- **一件事三条消息**：确认消息 + 任务卡片 + 结果消息。主 Agent 说话时还会出现 worker、任务、MCP 工具名这类内部词汇。

Muse 和 Grok Bot 的做法：

- **对话里只有消息**。你给目标，它在后台做事，完成后或需要你决定时才回来。
- **批准以卡片的形式出现在对话里**，用大白话写清它要做什么。
- **任务列表和执行记录收在单独的入口里**（Muse 在头像菜单下：任务列表、批准、即将发生的事、记忆）。
- **产出物单独归档**：Muse 的 Library 分「文档 / 媒体」。

**改法**：

1. 对话里只保留你和智能体的消息。
2. 智能体在做事时，只显示一条很轻的状态，例如「正在处理：整理周报」，不显示步骤。
3. 需要你回答的问题、需要你批准的操作、需要你接管浏览器的请求，以对话消息加按钮的形式出现，用大白话描述；具体命令折叠起来，需要时再看。
4. 产出的文件作为附件跟在结果消息后面，同时进入「成果」页。
5. 任务、批准、即将运行的定时任务、执行记录都放到「活动」页。技术细节（执行轨迹）只在活动页的任务详情里，并且默认折叠。
6. 主 Agent 用第一人称说话，不提 worker、任务、会话、工具名这些内部概念；确认消息加结果消息，一件事两句话。

## 二、架构与理念上的遗漏

| # | 文章 / 原型 | 现状 | 处理 |
|---|---|---|---|
| A | **主动**是四个基础特征之一（§1）。两级过滤：程序层 Fast Path + 语义层 Slow Path，语义层用提示词写的策略判断事件是否值得处理，并且是「面向人类的自然语言扩展点」（§3.1）。投机执行：静默复现并修复，有价值才交付，否则全程保持安静（§3.4）。原型的 accept mode（off / observe / auto）加规则 | 只处理有人 @ 它的请求。`filter` 层模型配置了，但从来没被调用。没有主动策略，没有投机执行 | **补上**：来源可以设置「接收全部消息」；Fast Path 用程序规则过滤；Slow Path 用 filter 层模型按你写的自然语言「主动策略」研判；分 off / observe（只记录「本来会做」）/ auto 三种模式；auto 模式下以「静默任务」投机执行，结果有价值才交付给你，否则安静丢弃 |
| B | 异步 `start()` / `stop()` 既用于耗时命令，也用于**子任务**（§4.1）；Worker 内部可以创建 Subagent（§2.2） | 只有异步的 shell 命令；`subagent` 模型层配置了但没有使用 | **补上**：Worker 的 `subagent_start` / `subagent_stop` 工具，子任务异步运行，完成后作为新事件送回 |
| C | Watchdog「可以让它在线修正主系统的行为，例如增删提示词、调整触发规则」（§6）；原型 004 里团队可以编辑提示词片段（沟通规范 / 任务范围 / 交付要求），并且有版本 | 没有可编辑的提示词；Watchdog 只能提醒任务或重启任务 | **补上**：「说明」三段（沟通方式 / 做事边界 / 交付要求），带版本；你提出要求时，主 Agent 和 Watchdog 可以修改说明和主动策略 |
| D | 原型 005：面板依次回答「现在有什么要我处理？系统健康吗？某件事从触发到结束的来龙去脉是什么？」 | 有设置页，但没有「活动」视图，无法追溯「为什么这条消息没人理」 | **补上**：活动页（待你处理 / 进行中 / 即将运行 / 主动观察记录 / 历史），每个触发事件的去向可以查 |
| E | 链式召回：Trigger → Thread → Worker → 另一个 Thread（§3.3） | `recall` 支持 task / trigger / conversation / blob，但读不了 thread 和 worker | **补上**：thread 和 worker 会话的召回，返回内容里内联下一跳的 ID |
| F | IM 信道单次回复不超过 100 词的硬性规定（§4.2） | 只写在提示词里 | **补上**：对话类信道的回复超长时，工具直接拒绝并要求精简；长内容改用附件 |
| G | 原型：主 Agent 每次决定都留下理由（Decision） | 主 Agent 不回复就等于忽略，没有任何记录 | **补上**：`ignore` 动作附带理由，每个触发事件都有去向记录 |

已经符合文章设计的部分（不改）：
- 双层架构，主 Agent 不配 Bash
- 批处理、订阅直通
- Inline & Spill
- 全双工的 shell 命令
- 多信道（GitHub 写长文，对话写短句）
- 计算与状态分离
- Watchdog 的探针
- 审核和凭据隔离

## 三、刻意保留的差异

- **允许多个对话**：文章说个人助手通常只有一个聊天页，但你明确要「单 agent、可以创建多个对话」，这一点照你的要求保留。每个对话就是一个话题，底层仍然是同一个智能体。
- **审核层、记忆、浏览器接管**：文章没有展开写，按 Grok Bot / Muse 的做法实现。

### 实测（真实模型 DeepSeek V4.1 Flash + 假 GitHub）
- 打招呼：直接回复。
- 写密码脚本：一句确认，完成后一条结果，附 `generate_passwords.py`、`passwords.txt`。
- 调研 SQLite WAL：附 markdown 文档和验证脚本。
- 说「以后先说结论」：写进说明第 1 版，下一条回复就先说结论。
- GitHub 上的感谢留言：判为不处理。
- 能复现的 bug 报告：悄悄复现并准备好补丁，只在网页里告诉你，GitHub 上没有发任何评论。
